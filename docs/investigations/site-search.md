# サイト内検索（日本語全文検索）方式の調査

- 対応Issue: #15
- 調査日: 2026-09-13
- ステータス: 調査完了・方式決定（実装は別issueで対応）

## 結論

**Pagefind**（ビルド後処理として静的検索インデックスを生成するツール）の採用を推奨する。

- GitHub Actions によるビルド後、`_site/` に対して `pagefind` を実行するだけで導入でき、Jekyllプラグインの追加や外部サービスへの依存が不要
- 日本語（CJK）のトークナイズを標準で内蔵しており、実機検証で分かち書きが機能することを確認した
- インデックスはページ単位・断片単位に分割されるため、検索語に応じて必要な断片のみを遅延ロードする設計であり、全文索引の一括配信によるロード遅延という懸念は生じない
- メンテナンス状況が良好（2026年に入っても継続的にリリースされている）

ただし、全角/半角の表記ゆれ吸収や条・項単位のディープリンクなど、精度・機能面の課題は別途対応が必要（詳細は後述）。実装（GitHub Actionsワークフローへの組み込み、検索UIの追加等）は本issueのスコープ外とし、別issueとして切り出す。

## 検討した候補

| 方式                                              | 概要                                                             | 日本語対応                                   | メンテナンス状況                                         |
| ------------------------------------------------- | ---------------------------------------------------------------- | -------------------------------------------- | -------------------------------------------------------- |
| (a) 自前JSON + lunr.js/Fuse.js/MiniSearch         | Liquidで`search.json`を生成し、クライアントサイドJSで検索        | 追加のトークナイザ実装が必要                 | ライブラリ自体は概ね健全だが自前実装の保守が必要         |
| (b-1) **Pagefind**                                | ビルド後処理として静的サイトの生成物からインデックスを作成       | 標準で対応（`Intl.Segmenter`ベース）         | 良好（2026年も継続リリース）                             |
| (b-2) jekyll-lunr-js-search 等のJekyllプラグイン  | Jekyllプラグインとしてビルド時にlunr.jsインデックスを生成        | 標準では非対応（lunr-languages等が別途必要） | 停止・非推奨のものがほとんど（詳細は後述）               |
| (c) 外部SaaS（Algolia DocSearch / Google PSE 等） | 本文を外部サービスにクロール・登録し、検索もそのサービス側で処理 | サービス依存                                 | サービス自体は健全だが、本文の学外送信という別の懸念あり |

## 実機PoCによる検証

`_rules/`（148件）を実際に `bundle exec jekyll build` でビルドし、生成された `_site/`（149ページ、2.3MB）に対して `npx pagefind --site _site` を実行して検証した。

### ビルド・インデックス生成結果

```
Discovered 1 language: ja
Indexed 1 language
Indexed 149 pages
Indexed 5444 words
Note: Pagefind doesn't support stemming for the language ja.
Search will still work, but will not match across root words.
```

生成された `_site/pagefind/` は合計1.9MB。内訳は以下の通り:

- 共通ランタイム（`pagefind.js`、`pagefind-ui.js`、wasmバイナリ、CSS等）: 合計約440KB。初回アクセス時のみ取得され、以降はブラウザキャッシュされる
- 言語別インデックス本体（`index/ja_*.pf_index`）: 1ファイルあたり28〜40KB、148ファイルに分割されている。検索語に応じて該当する断片のみを遅延ロードする設計であり、全件を一括ダウンロードすることはない

issueに記載の見積り（5件で109KB→148件で約3MB）に対し、148件変換完了後の実測は `_rules/` で1.9MBだった。Pagefindの断片分割設計により、この規模であっても初回ロードの重さは実用上問題にならないと判断できる。

### 検索UIでの動作確認

`pagefind-ui`（標準UIコンポーネント）を組み込んだテストページをローカルサーバで配信し、ブラウザから実際に検索して以下を確認した。

| クエリ           | 結果件数  | 所見                                                                                                   |
| ---------------- | --------- | ------------------------------------------------------------------------------------------------------ |
| `秋田県`         | 28件      | スニペットに単語単位のハイライトが表示され、日本語の分かち書きが機能していることを確認                 |
| `第１条`（全角） | 147/149件 | ほぼ全ての規程が第１条を持つため、想定通りの挙動                                                       |
| `第1条`（半角）  | 31件のみ  | 「第」「条」に部分一致した結果を返しているに過ぎず、本文中の全角表記「第１条」を正しく検出できていない |

**全角/半角の表記ゆれはPagefind側では吸収されないことを実機で確認した。** 対応するには、インデックス生成前にHTML側で正規化（例: 半角表記を隠しテキストとして併記する、または本文自体を正規化する）を行う前処理が別途必要になる。「規程」/「規定」等の同義語についても同様で、Pagefind自体に同義語辞書の機能はない。

## 各懸念点への回答

### 1. 候補の比較検討

上記の通り。Pagefindは「ビルド後処理」であるためJekyllプラグインである必要がなく、GitHub Actionsのワークフローに1ステップ追加するだけで導入できる点が、自前実装（a）やJekyllプラグイン依存（b-2）に対する明確な優位点。

### 2. 日本語の分かち書き（トークナイズ）

- **Pagefind**: 標準で`Intl.Segmenter`ベースのCJK分かち書きを内蔵。追加設定なしで実機検証において妥当な分かち書き結果を確認した
- **lunr.js + lunr-languages**: `lunr.ja.js`が存在し、TinySegmenter（辞書不要の統計的手法、約23KB）を使用する。lunr-languages自体は2026年8月にもリリースがあり活発にメンテナンスされているが、TinySegmenterはニュース記事程度の文章で約95%程度の精度とされ、法規文書特有の専門用語・固有名詞には辞書ベース（MeCab等）に劣ると考えられる
- 総合的に、追加のトークナイザ導入や設定が不要なPagefindの方が実装・保守コストの面で優位

### 3. インデックスサイズの見積り

上記PoC参照。全148件変換完了後の実測は`_rules/`で1.9MB、ビルド後`_site/`で2.3MB。Pagefindのインデックスは断片分割・遅延ロード設計のため、単一JSON配信を前提とした懸念（初回ロードが重い）はそもそも当てはまらない。

### 4. 検索結果の粒度

現在生成されるMarkdown/HTMLには条・項単位の`id`が振られておらず、Pagefindは規程（ページ）単位でのヒット・スニペット表示となる。条単位のディープリンクを実現するには、`scripts/convert_to_markdown.py`または`_layouts/rule.html`側で条ごとに`id`属性を付与する対応が別途必要。**本issueでは方式の選定に留め、条単位のディープリンク対応は別issueとして切り出すことを推奨する**（issueの想定通り）。

### 5. 日本語の表記ゆれへの対応

実機検証の結果、全角/半角数字の表記ゆれはPagefind側では吸収されないことを確認した（上記参照）。「規程」/「規定」等の同義語も同様に非対応。これらはインデックス生成前の前処理（正規化・同義語展開）で対応する必要があるが、初期導入時点では素の全文検索を提供し、運用しながら段階的に精度を改善する方針で問題ないと考える。

### 6. 非公開リポジトリから公開Pagesを構築する場合の制約（外部SaaS利用の可否）

Algolia DocSearchは2026年に無料枠の対象が「技術文書サイト全般」に拡大されたが、審査基準は「開発者向けドキュメント/技術ブログ」であり、大学の法規文書サイトが該当するかは不明瞭（要問合せ）。採用可否によらず、**規程本文がAlgolia側のグローバルインフラにクロール・複製され、検索時もAlgolia側で処理される**ことになり、これは本文を学外のサービスに送信することを意味する。Google Programmable Search Engineも同様に本文がGoogle側に渡る。

**本文を学外サービスに送信することを大学として許容できるかは、本調査の範囲では判断できない。#8と共通の論点であり、別途大学として確認が必要な事項として明記する。** なお、Pagefindは静的サイト内で完結し外部送信が発生しないため、この懸念自体を回避できる点も採用理由の一つである。

## Jekyll専用の検索プラグインについて（追加調査）

Jekyll向けに専用設計された検索プラグイン・gemの現状も調査した。

- **jekyll-lunr-js-search**: 2018年で開発停止（`[UNSUPPORTED]`表記、issueも未対応のまま放置）。最新リリースは2017年。Jekyll 4.x / Ruby 3.4系での動作実績はなく、依存gem（nokogiri等）のバージョン制約から現行環境へのインストールも困難と見られる。CJK対応もなし。**不採用**
- **simple-jekyll-search**: 2022年にアーカイブ済み（開発停止）。トークナイズを行わない単純な部分一致検索であり、たまたま日本語でも動作はするが、関連度ランキングや表記ゆれ対応は期待できない。**不採用**
- **jekyll-algolia**: 2023年10月を最後に更新停止。Algolia依存のため懸念6と同じ問題を抱える。**不採用**
- **jekyll-meilisearch**: 2025年時点では更新があるものの、Meilisearchサーバの自前運用が必要であり、「サーバサイド処理を持たない静的サイト」という前提と矛盾する。**不採用**
- **jekyll_pages_api_search（18F）、searchyll等**: 明示的に非推奨、または外部検索エンジン（Elasticsearch等）への依存が必須。**不採用**

現状、Jekyll専用の検索プラグインで実用に足るものは見当たらなかった。Pagefindはビルド後処理として動作するためJekyllプラグインである必要がなく、コミュニティ製のJekyll向けラッパー（`phothinmg/jekykll-pagefind`など）も存在するが、GitHub Actionsのワークフロー上で`jekyll build`の後に`npx pagefind --site _site`を実行するだけで十分に簡潔なため、追加のJekyllプラグイン導入は不要と判断する。

## 今後の課題（別issueで対応）

- Pagefindの導入自体（GitHub Actionsワークフローへの組み込み、検索UIのレイアウトへの追加）
- 全角/半角・「規程」/「規定」等の表記ゆれ正規化（インデックス生成前の前処理として実装）
- 条・項単位への`id`付与とディープリンク対応
- 外部SaaS利用（Algolia DocSearch等）を選択肢とする場合の、本文の学外送信に関する大学としての許容性確認（#8と共通）
