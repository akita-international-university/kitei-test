## 結論・対応方針

方針どおり、以下の2段階で対応した。

1. **変換スクリプト側で改善可能なもの**: `header_row_count()` がrowspanのみに基づく推定のため見出し行数を誤検出していた2ファイルについて、`scripts/convert_to_markdown.py` に個別の上書き機構を追加して修正した（後述）。
2. **個別対応が必要なもの**: 見出しの結合セル（colspan）が下位の列を区別する見出しを持たないために生じる「隣接列の見出し文言の完全重複」が8ファイル9表で見つかった。これは元のHTML自体がその列を区別する文言を持たないことに起因しており、スクリプト側で新たな文言を創作すると「内容を保つ」という最優先方針に反するおそれがあるため、自動修正はせず本ドキュメントに一覧化した。最終的に見出し文言を調整するかどうかは、原本を確認した上での人による判断が必要。

いずれの場合も、個別のMarkdownファイルを直接手編集するのではなく、(1)はスクリプトの改修、(2)は本ドキュメントへの記録という形で対応した。これは、現行の規程管理システムからの移行に伴いHTML抽出・変換作業が今後も繰り返される可能性があり、変換の最終実行後に個別修正を行うことで手戻り（先祖返り）のリスクを減らすため。

## スクリプト側で対応した項目（対応済み）

### 症状

`header_row_count()` は「先頭行のセルの最大rowspan」を見出し行数とみなす実装になっている。この前提は、見出しが複数行にまたがる典型例（例: 1列目の見出しセルがrowspanで2行分結合されている）では機能するが、**先頭列自体が見出し行ごとに異なる文言を持つため、どのセルにもrowspanが付かない表**では機能しない。

具体例（`国際教養大学における短時間労働者就業規程.html` 別表、`国際教養大学非常勤教員就業規程.html` 別表 ― 内容は同一。表の行は元HTMLの`<tr>`にそのまま対応し、罫線はcolspan/rowspanの区切りを示す）:

```
[１週間の平均所定労働時間] | [３０時間以上] | [３０時間未満](colspan=5)
[１週間の平均所定労働日数] | [―] | [５日以上] | [４日] | [３日] | [２日] | [１日]
[年次有給休暇日数]         | [１０日] | [１０日] | [７日] | [５日] | [３日] | [１日]
```

1行目にrowspanが無いため見出し行数は1と推定され、本来は2行目まで見出しとして扱うべき「週所定労働日数の区分」が、独立したデータ行として出力されていた（＝年次有給休暇日数の各列がどの労働日数区分に対応するかの見出しが失われる）。

### 汎用的な修正を試みたが断念した経緯（記録）

「直前の見出し行にcolspan由来の重複が残っており、次の行がそれを個別の値に分解していればその行も見出しとみなす」という汎用ヒューリスティックを実装して全148ファイルで検証したところ、上記2ファイルは正しく修正される一方、以下の2ファイルで**誤って本来のデータ行を見出しに取り込んでしまう**回帰が発生した。

- `国際教養大学における授業料等取扱規程.html`: 「区分」列の直後にある最初のデータ行（授業料の行）を見出しに取り込んでしまう
- `国際教養大学学生生活規程.html`: 番号付き一覧の最初のデータ行（「１｜在学証明書」）を見出しに取り込んでしまう

原因は、「次の行が列ごとに異なる値を持つ」という条件が、見出し行の継続だけでなく**ごく普通のデータ行**でも当然に成立してしまうため（データ行は通常、列ごとに異なる値を持つのが自然な姿であり、見出し行かどうかの判別材料にならない）。元HTMLには見出しセル（`<th>`）とデータセル（`<td>`）の区別が無く、全て`<td>`で書かれているため、構造的にこの2パターンを汎用的に見分ける手がかりが存在しないと判断した。

### 採用した対応

汎用ヒューリスティックの変更は断念し、代わりに `scripts/convert_to_markdown.py` に **(元HTMLファイル名, 表divのid) をキーとする見出し行数の個別上書き表**（`TABLE_HEADER_ROWS_OVERRIDE`）を追加し、該当2件のみ確認済みの値（2行）を明示的に指定するようにした。この方式であれば、

- 他の146ファイルの変換結果には一切影響しない（実際に確認済み。詳細は後述）
- 個別のMarkdownファイルを手編集するわけではないため、`poetry run convert2markdown` の再実行（元HTMLの再取得・全件再変換）を経ても修正が保持される

という2点を両立できる。

### 修正の確認

修正前後で `poetry run convert2markdown`（全件変換）を実行し、生成された148件の `_rules/*.md` を比較した。変更があったのは意図した2ファイルのみで、他146ファイルへの影響は無いことを確認した。また `poetry run verifyconversion` を再実行し、内容欠落チェックが引き続き0件であることも確認した。
